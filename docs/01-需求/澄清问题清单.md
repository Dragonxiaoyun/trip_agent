## A. MVP 范围(决定我们第一个版本做什么)

- **Q1.** MVP 是否只包含三大件:**行程生成 + 预算统计 + 地图路线**?
  建议:是。**行程编辑(增删改联动)** 和 **PDF/图片导出** 放二期——原始需求文档(raw/业务需求文档-v0.md)自己也标注了编辑联动"好难",它是技术复杂度最高的功能,不适合首发。
- **Q2.** "交通"在 MVP 里管到哪一层?
  建议:MVP 只规划**往返大交通方案推荐**(飞机/高铁对比、价格区间、耗时)+ **当地每日交通方式**(包车/公交/打车建议),不做实时票务查询和预订跳转。
  → **2026-10-21 修订(RP-1)**:"无合规个人 API"结论被调研推翻——飞常准 MCP 为合规渠道,机票实时价格与火车票时刻/余票/票价实时查询已纳入 MVP(P0);2026-10-27 起大交通推荐另含自驾对比(见需求规格 F2/AC-24)。
- **Q3.** 用户系统:MVP 是否需要注册登录、保存历史行程?
  建议:MVP **免登录**,行程生成后给唯一链接可回看;用户体系放二期。这能砍掉鉴权、数据隔离一大块架构工作。
- **Q4.** 原始需求文档提到"精确程度可调节"。MVP 行程粒度定在哪?
  建议:精确到**上午/下午/晚上三个时间块**,每块 1-2 个活动;小时级排期(几点到几点)放二期。小时级需要真实 POI 开放时间和路程耗时数据,MVP 数据源撑不住。

## B. 输入与业务规则(决定需求规格里的字段和校验)

- **Q5.** 输入字段确认:出发地、目的地、日期(起止或天数)、人数、总预算、偏好标签。预算口径是**总预算**还是**人均**?是否提供"穷游/舒适/豪华"快捷档位?
  建议:预算用**人均总预算**,同时提供三档快捷选择;偏好用标签多选(自然风光/历史文化/美食/小众秘境/亲子…)+ 自由文本补充。
  → **已被 Q19/Q21 两次修订**:预算改双口径输入(总预算/人均任填其一),预算人数=成人+老人+0.5×儿童;三档重新定义为消费档位偏好(不定金额,默认舒适),预算金额改非必填。
- **Q6.** 家庭出游场景:是否需要输入**儿童/老人人数**?这会影响节奏(每日景点数)、住宿(家庭房)、景点筛选(强度)。
  建议:需要,作为可选字段;有老人儿童时 Agent 自动降低每日行程密度。
- **Q7.** 预算超支规则:生成结果超过预算多少算"超"?超了怎么办?
  建议:预算按 ±15% 浮动视为达标;超出则 Agent 必须给出 2-3 个降级方案(换酒店档位/减少付费景点)供用户选。
  → **已被 Q24 与 AC-18 细化**:预算分不可行/紧张/达标三区;超支触发口径为"超出预算上限 >15%(恰好 15% 不触发)";节余 >15% 给非阻断升级提示(AC-18)。
- **Q19.(2026-10-22 补充)** "人均总预算"是总预算还是每个人的预算?输入口径与儿童如何计价?
  结论:①指"每个人全程所有分类的合计预算";②输入双口径——用户可填**总预算**或**人均预算**,任填其一,另一个自动换算;③儿童按 **0.5 个成人**计入预算人数(门票半价/免票、不占床),即预算人数 = 成人 + 老人 + 0.5×儿童,预算上限 = 人均 × 预算人数。本条为 Q5 答案的修订。
- **Q20.(2026-10-22 补充)** 目的地能否支持国家级(如泰国)?是否意味出境游进 MVP?
  结论:输入层面支持国家级;但出境游行程生成仍留二期——MVP 选择出境目的地时提示"出境游二期上线",不生成行程。连带项(国外地图 Mapbox、国际机票 Amadeus、签证/汇率注意事项)维持二期决议不变。出发地保持城市级(大交通须从具体城市起算)。
- **Q24.(2026-10-22 补充)** 极端低预算(如新疆7天3成人、人均200元)怎么办?AC-4 的降级方案对此是否失效?
  结论:预算分三区——不可行区/紧张区/达标区,AC-4 只覆盖紧张区。新增前置可行性校验:预算 < 硬成本下限(往返大交通最低价+最低价住宿×天数+生存线餐饮×天数,飞常准/RollingGo 实时数据经 calculator 计算)→ 拒绝生成,返回不可行说明+最低可行参考预算+调整建议(提高预算/缩短天数/换近目的地),不得强行生成无法执行的行程;下限校验在生成前执行,同时避免浪费一次 90 秒生成。AC-4 加"预算 ≥ 硬成本下限"前置条件,新增 AC-17。
- **Q21.(2026-10-22 补充)** 三档(穷游/舒适/豪华)的金额标准如何界定?目的地物价和天数差异太大,是否有必要保留?
  结论:保留但**重新定义为消费档位偏好**(可选,默认舒适)——不定金额、定资源映射(住宿星级/餐饮档次/舱位等,见需求规格 §4 档位映射表);预算金额改为**非必填**(双口径不变);仅选档位未填金额时,系统按档位生成行程并用真实查询数据估算参考预算(标注"档位估算参考",无超支判定),解决"不知道预算多少"用户的引导问题。本条为 Q5 答案的第二次修订。
- **Q22.(2026-10-22 补充)** 酒店价格能否纳入降价提醒?注意事项(F8)的数据源是什么?穆斯林国家等特殊风俗地区如何保证覆盖?
  结论:①F15 扩展至酒店——RollingGo 定时查价监控(官方支持 24 小时盯价能力),同房型降价推送;②注意事项数据源定为三层结构:LLM 主答文化风俗禁忌等稳定知识(训练数据覆盖充分)、搜索工具校验签证/管制/公告等时效项且**官方源优先**(领事服务网、文旅部门)、小红书知识库补充真实旅行者经验;③时效性条目必须标注来源与查询日期(AC-15),特殊风俗目的地(新疆、穆斯林国家)必须输出对应禁忌条目。
- **Q23.(2026-10-22 补充)** 餐饮能否接实时点评数据、总结好评差评?
  结论:平台评论直连不可行(大众点评无合规 API,爬虫已排除);修订为"代表店附口碑摘要"——评分/人均消费来自高德 POI 实时查询,好评/差评要点由搜索工具+小红书知识库经 LLM 总结并标注来源与时间,搜不到如实标注"暂无足够口碑数据"不得编造;国外二期用 Google Places 真实评论(绑卡门槛 M1 核实)。本条修订 §7 第 5 条,新增 AC-16。

## C. 数据源与可行性(本阶段最关键,直接决定架构)

- **Q8.** 地图:是否有**高德或百度地图开放平台账号**?前端地图展示、POI 标注、路线绘制必须用其 Web API(个人开发者有免费额度)。
  建议:高德(JS API + Web 服务 API 生态最全)。如没有,注册只需实名认证,我可以给注册指引。
- **Q9.** 机酒真实价格:原始需求文档设想调携程查机票酒店——**携程没有面向个人开发者的开放 API**。MVP 可接受的替代方案是哪个?
  - a) LLM 基于训练知识给出**价格区间估算** + 标注"仅供参考",附携程/飞猪搜索链接(建议,MVP 够用)
  - b) 接入聚合比价 API(如 Skyscanner/航班管家,部分有免费层,覆盖不全)
  - c) 爬虫抓携程(有合规风险,不建议)
  → **2026-10-22 修订(RP-1/RP-6)**:机票/火车票经飞常准 MCP(RP-1)、酒店经 RollingGo MCP(RP-6)升级为实时查询;查询失败降级为 LLM 区间估算+AC-10 标注,原"降级用聚合比价 API"答案不再采用。
- **Q10.** 景点门票/餐饮数据:接受 **LLM 知识 + 联网搜索工具**的组合吗?还是要求接具体数据 API?
  建议:MVP 用 LLM 知识为主 + 搜索工具校验时效性信息(门票价格、开放状态);餐饮推荐到"片区+品类+代表店"级别,不做实时点评数据。
- **Q11.** 天气:免费 API 可以吗?新疆 7 天行程,天气预报只能覆盖未来 7-15 天,远期出行只能给**历史同期气候参考**。
  建议:和风天气免费版;出行日期超出预报范围时自动切换为历史气候描述,并在 UI 标注区别。
- **Q17.(2026-10-22 补充)** 景点门票价格的数据源是什么?国内美团/携程门票均无个人开放 API。
  结论:LLM 知识给出价格区间 + 搜索工具校验时效性(价格/开放状态/预约政策),按 AC-10 标注"估算仅供参考";国外二期候选 Klook/Tiqets(实时价格库存,合作伙伴审批制)。
- **Q18.(2026-10-22 补充)** 预算如何计算?直接让 LLM 算加总可靠吗?
  结论:不可靠,禁止 LLM 心算加总。预算的分类加总/总计/人均/±15% 超支判定必须经 calculator 工具(tools/ 层纯代码运算);Agent 只收集价格参数并组装结构化预算对象,AC-3"各分类之和=总计"由代码保证。

## D. 非功能约束(影响架构与成本设计)

- **Q12.** DeepSeek-V4-Pro-0813 的 API Key 已申请了吗?走官方平台还是第三方代理?**月成本预算上限大概多少?**
  (影响:是否要做缓存、是否分层用便宜模型处理简单任务。注:该模型名的可用性和定价我会在 M1 用 WebSearch 核实并写入 ADR。)
- **Q13.** 生成耗时容忍度:一次完整的 7 天行程生成(多轮工具调用)预计 30 秒-2 分钟。接受**异步生成 + 流式进度展示**吗?
  建议:必须接受,同步等待体验不可行;前端做"正在查询天气…正在规划路线…"的分步进度。
- **Q14.** 并发与规模:MVP 的使用规模是?
  建议:按"自用 + 小范围种子用户(<100 人)"设计,不做过早的水平扩容,但架构上不留单点硬编码。
