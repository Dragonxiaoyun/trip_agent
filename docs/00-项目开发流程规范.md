# 项目开发流程规范（trip_agent 智能旅行助手）

> 状态：定稿 | 制定：2026-10-21 | 变更记录见文末

本文档是本项目的"宪法"：开发流程、代码规范、目录规范、开发规范、AI 应用特有规范，均以本文档为准。所有后续文档与代码必须遵守本文档。

---

## 1. 总则与核心原则

1. **文档先行**：任何代码被写入之前，其对应的设计文档必须已定稿。未定稿的需求/设计，一律不实现。
2. **单一事实来源**：需求以 `docs/01-需求/` 为准；架构决策以 `docs/02-架构/` 的 ADR（架构决策记录）为准；接口契约以 `docs/03-设计/` 为准。代码注释与文档冲突时，以文档为对，并修正代码。
3. **小步快跑、垂直切片**：不做"先搭完所有模块再联调"。先打通一条最小端到端链路（walking skeleton），再按功能逐个迭代。
4. **可评估，不接受"感觉好用"**：所有 AI 行为必须有评估集（golden set）和可量化的验收标准。
5. **可追踪、可回滚**：prompt、模型、架构的每次变更都要记录（ADR / 变更日志），知道"为什么当时这么做"。
6. **规范即代码**：规范通过工具链强制（ruff / mypy / pytest），不靠自觉。

---

## 2. 角色分工与决策规则

| 角色 | 由谁担任 | 职责 |
|---|---|---|
| 产品负责人 / 验收人 | **你** | 提供需求与业务知识；回答澄清问题；确认/否决每个里程碑的交付物 |
| 架构师 / 工程师 | **Claude** | 出方案（ADR）、写设计文档、写代码、写测试、同步文档 |

**决策规则**：
- 需求决策（做什么、验收标准）：由你拍板，我只负责暴露歧义、给出专业建议。
- 技术决策（选什么框架、怎么分层）：我提案并写入 ADR（含理由与备选方案），你确认或否决。
- 发生分歧时：以 ADR 记录为准，先落地，后复盘。

## 3. 开发流程：里程碑制（M0 ~ M6）

每个里程碑有明确的：**输入物 → 产出物 → 验收标准 → 你需要做什么**。前一里程碑验收通过才进入下一里程碑。

| 阶段 | 目标 | 我产出 | 你需要提供 / 做 |
|---|---|---|---|
| **M0 需求定稿** | 需求无歧义，有可验收标准 | 澄清问题清单 → 需求规格文档（含功能清单、验收标准） | 提供：业务需求文档、简单设计文档（原文放进 `docs/01-需求/raw/`）；回答澄清问题；确认需求规格 |
| **M1 架构设计** | 技术选型与系统架构定稿 | 架构设计文档 + ADR 决策记录 + 技术选型对比 | 确认或修改技术选型；提供部署环境、LLM 账号/Key 情况 |
| **M2 项目骨架** | 规范落地，脚手架就绪 | 目录结构、工程配置、工具链（ruff/mypy/pytest）、git 初始化、CI 基础、示例模块 | 确认规范；确认技术栈工具链 |
| **M3 核心闭环** | 最小端到端链路可用 | 一个垂直切片：用户提问 → Agent 规划 → 工具调用 → 结构化输出 → 前端展示 | 按验收标准验收演示；提出现场反馈 |
| **M4 功能迭代** | 逐功能交付（行程规划、目的地推荐、预算助手…） | 每功能五步走：任务规格 → 实现 → 测试 → 自审 → 交付 | 逐功能验收；补充业务规则细节 |
| **M5 评估调优** | 效果可量化、可持续迭代 | golden set 评估集、评估报告、prompt/Agent 迭代方案 | 提供真实用例、bad case、使用反馈 |
| **M6 发布运维** | 上线并可持续运营 | 部署方案、监控方案、成本与安全检查清单 | 提供部署环境、密钥、域名等 |

**M4 的单功能五步走（核心工作流）**：

```
1. 任务规格    docs/04-任务/ 新增规格：需求编号、范围、验收标准（必须引用 M0 的需求编号）
2. 实现        按规格写代码；prompt 放 agents/prompts/，不散落在业务代码里
3. 测试        单元测试 + （涉 AI 的）评估用例；全部通过
4. 自审        对照第 8 节 DoD 清单逐项检查
5. 交付验收    给你演示 + 验收标准逐条核对；通过后规格标为"已完成"
```

## 4. 文档体系与目录规范

### 4.1 docs/ 目录结构

```
docs/
├── README.md                 # 文档索引（每篇文档一行，标注状态）
├── 00-项目开发流程规范.md      # 本文档
├── 00-架构师工具手册.md       # 配套：各阶段人工干预点与工具调用指南
├── 01-需求/                   # M0 产出
│   ├── raw/                   # 你提供的原始文档（只读，不改）
│   ├── 需求规格.md             # 澄清后的定稿需求 + 验收标准
│   └── 变更记录.md
├── 02-架构/                   # M1 产出
│   ├── 架构设计.md
│   └── adr/                   # 每决策一文件：ADR-0001-xxx.md
├── 03-设计/                   # 详细设计（M1/M4 持续产出）
│   ├── api/                   # 接口契约（OpenAPI / 接口说明）
│   ├── 数据模型.md
│   ├── agent设计/              # 每个 Agent：职责、工具、prompt 设计说明
│   └── 错误处理.md
├── 04-任务/                   # M4 的任务规格，一任务一文件，标注状态
├── 05-评估/                   # M5：golden set、评估报告、bad case 库
└── 06-运维/                   # M6：部署、监控、成本、安全清单
```

### 4.2 文档规范

- **命名**：中文文件名，序号前缀；ADR 用 `ADR-NNNN-短横线标题.md`。
- **头部**：每篇文档必须有状态行：`> 状态：草案 | 评审中 | 定稿 · 最后更新：YYYY-MM-DD`。
- **状态流转**：草案 → 评审中（我们讨论）→ 定稿（你确认）。定稿后修改必须走第 9 节变更流程。
- **验收标准必须可执行**：写成"给定 X，当 Y，则 Z"的形式，不用"体验良好"这类词。

## 5. 代码规范

### 5.1 语言与格式

- **语言**：Python 3.11+，类型注解全覆盖；对外 API 契约用 Pydantic v2 定义。
- **格式化/静态检查**：`ruff format`（格式化）+ `ruff check`（lint）+ `mypy --strict`（类型）。三者全部通过才算"代码可交付"。
- **测试**：pytest；业务服务与工具层必须有单元测试；涉 LLM 的逻辑必须有评估用例（见 5.5）。
- **命名**：标识符一律英文 snake_case（变量/函数）、PascalCase（类）、UPPER_CASE（常量）；注释与文档字符串用中文；禁止拼音命名。
- **docstring**：公开函数/类必须写 docstring（中文，说明用途、参数、异常）。

### 5.2 提交规范

- 提交信息用 [Conventional Commits](https://www.conventionalcommits.org/)：`feat:` / `fix:` / `docs:` / `refactor:` / `test:` / `chore:`，例如 `feat(agent): 增加行程规划工具的天气降级逻辑`。
- 一次提交只做一件事；文档与代码可同提交（保持同步是好事）。
- 每个功能分支以 `feat/xxx` 命名；main 分支上任何时刻代码都必须是可运行的。

## 6. 代码目录规范（backend，Python/FastAPI）

分层依赖规则：**上层可依赖下层，下层禁止依赖上层，同层尽量解耦。**

```
backend/
├── app/
│   ├── main.py              # 应用入口：装配依赖、注册路由
│   ├── config/              # 配置（pydantic-settings），密钥只走环境变量
│   ├── api/                 # HTTP 路由层（薄）：参数校验、调用 service、拼响应
│   ├── schemas/             # Pydantic 契约：请求/响应/Agent 结构化输出
│   ├── services/            # 业务服务：行程、用户画像等业务逻辑
│   ├── agents/              # Agent 层：agent 定义、编排逻辑
│   │   └── prompts/         # prompt 即代码：每 prompt 一文件，版本管理
│   ├── tools/               # 工具实现：搜索、天气、地图…（不知道 agent 存在）
│   ├── llm/                 # LLM 客户端封装：调用、tracing、重试、成本统计
│   └── models/              # 数据访问层（ORM / repository）
├── tests/                   # 测试（与 app/ 目录结构镜像）
├── pyproject.toml           # 依赖与工具链配置（ruff/mypy/pytest）
└── README.md                # 如何启动、如何跑测试、如何跑评估
```

关键约束：

1. `api/` 是薄层：不写业务逻辑，只做校验与转发。
2. `tools/` 不知道 agent 的存在：任何工具必须可以独立测试、独立复用；工具只返回结构化结果，不做用户可见的文案拼装（文案由 agent/prompt 层负责）。
3. `llm/` 是唯一允许调用模型 SDK 的层；业务代码不得直接调 SDK。
4. prompt 文本全部放 `agents/prompts/`，一个 prompt 一个文件；业务代码中禁止内联超过 2 行的 prompt 字符串。
5. 前端目录 `frontend/` 在 M1 确认技术栈后补充规范。

## 7. 开发规范（DoD：交付完成的定义）

每次交付（含每个任务、每个里程碑）前，必须逐项自检：

- [ ] `pytest` 全部通过（新增逻辑有对应测试）
- [ ] `ruff check` 与 `ruff format` 通过
- [ ] `mypy --strict` 通过
- [ ] 本次改动影响到的文档已同步更新（文档与代码不脱节）
- [ ] 涉及 AI 行为（prompt / 工具描述 / 模型参数）变更：评估集已跑并记录对比结果
- [ ] 涉及架构决策：已有对应 ADR
- [ ] 验收标准逐条核对完毕（交付时附核对结果，而非只给代码）

## 8. AI 应用特有规范（本项目的重点）

AI 应用与传统应用的差异在于：**核心行为由模型决定，行为不可 100% 复现，必须用工程手段约束。** 以下规范贯穿全程：

1. **Prompt 即代码**：prompt 与代码同仓库、同版本、同评审。每次修改记录"为什么改"。禁止在业务代码里拼接大段 prompt。
2. **结构化输出强制校验**：LLM 输出必须经 Pydantic schema 校验；校验失败 → 带错误信息重试（≤2 次）→ 仍失败则降级（返回明确错误或安全兜底文案），绝不把脏数据传给下游。
3. **评估驱动（eval-driven）**：每个核心场景（如"规划 3 天上海行程"）在 `docs/05-评估/` 有 golden case（输入、期望要点、评分维度）。任何 prompt/模型/工具描述变更，必须跑评估集对比通过才可交付。
4. **可观测性**：每次 LLM 调用必须记录：输入/输出、token 用量、延迟、成本、工具调用链、最终是否校验失败。本地开发用结构化日志 + 本地 trace 文件；M6 前评估是否接入 Langfuse 等平台。
5. **容错与降级**：LLM 超时/限流 → 指数退避重试 → 降级回复；工具调用失败 → 把错误作为上下文回传 agent 决定下一步，不允许异常直接抛给用户。
6. **成本控制**：区分任务复杂度选模型（简单意图用便宜模型）；敏感信息不进 prompt 的无关上下文；长对话做摘要压缩。
7. **安全**：工具权限最小化（只读工具绝不开放写权限）；对工具入参做白名单校验；日志与 trace 中脱敏 PII（姓名、手机号、身份证）。
8. **工具契约**：每个工具必须有：名称、功能描述（给模型看，决定调用质量）、参数 schema、返回 schema、副作用声明。给模型看的描述文本变更 = 评估集必须重跑。

## 9. 变更管理

| 变更类型 | 流程 |
|---|---|
| 需求变更 | 在 `docs/01-需求/变更记录.md` 追加：变更内容、影响面、决策人；先改文档，再改代码 |
| 架构/技术决策变更 | 新写一篇 ADR（说明推翻/修订哪篇），你确认后生效 |
| prompt / 模型 / 工具描述变更 | 记录理由 → 跑评估集对比 → 你确认 → 合并 |
| 本规范变更 | 提案 → 我们讨论 → 你确认 → 更新本文档并标注变更记录 |
