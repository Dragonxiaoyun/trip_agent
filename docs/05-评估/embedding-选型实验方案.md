# Embedding 模型选型实验方案:Qwen3-Embedding-0.6B vs BGE-M3

> 状态:草案 · 最后更新:2026-10-28

## 1. 背景与目标

trip_agent 需要构建旅行攻略知识库(RAG),原始语料以小红书攻略笔记为主。向量库选型已定路线(pgvector 起步,规模增长后可平滑迁移 Qdrant/Milvus,迁移方案另文记录),embedding 模型未定。

本文档定义一次小成本对比实验,用可量化指标在两个候选模型之间做选型裁决。实验产出的 golden set、标注规范与 bad case 库将直接沉淀为 M5 评估资产,选型结论将作为 M1 阶段 ADR(embedding 模型选型)的输入。

**已决策项(不在本实验范围内)**:

- embedding 层必须做成可插拔接口,模型名、向量维度、运行设备均走配置,禁止硬编码(遵循 AGENTS.md「模型参数必须可配置」铁律);两个候选模型都要接入。
- 向量检索底座用 pgvector,与主库 PostgreSQL 复用。

**待裁决项**:默认 embedding 模型选 Qwen3-Embedding-0.6B 还是 BGE-M3,以及是否需要混合检索(稠密 + 稀疏/BM25)。

## 2. 候选方案与对照组

| 组 | 配置 | 说明 |
|---|---|---|
| A | Qwen3-Embedding-0.6B(稠密,维度 1024) | 当前 MTEB 多语言/中文 CMTEB 得分更高(64.33 vs 59.56);Apache 2.0;支持 instruction |
| B | BGE-M3(仅稠密,维度 1024) | 控制变量,纯稠密对比纯稠密 |
| C | BGE-M3(稠密 + 稀疏混合) | 发挥 BGE-M3 独有能力,检验混合检索对 POI 名称类查询的收益 |

- A、B 两组向量维度统一取 1024(Qwen3-Embedding 支持可变维度,取 1024 与 BGE-M3 对齐,消除维度变量)。
- 距离度量统一 cosine。
- 若 C 组显著优于 A,追加一轮「A + PostgreSQL tsvector BM25 混合」对照,确认混合收益能否脱离 BGE-M3 单独获得。

## 3. 实验语料

| 项 | 标准 |
|---|---|
| 来源 | 优先真实小红书旅行攻略笔记(手工收集或合规渠道获取,仅用于内部评估,不入库分发);流程跑通阶段可用合成语料,但选型结论必须以真实语料复核 |
| 规模 | ≥ 50 篇笔记,覆盖 ≥ 3 个目的地城市、含餐饮/景点/交通多主题 |
| 切分 | 固定切分策略(建议 256~512 字、重叠 10%),切分后约 500~1000 个 chunk;切分策略在两组间完全一致 |
| 存储 | chunk 原文 + 元数据(笔记 ID、城市、主题、来源)+ `embedding_model_version`,即 chunk registry, Postgres 保存,作为唯一事实来源 |

## 4. 查询集与标注(golden set)

**查询集**:30 条真实风格的用户查询,按 4 个切片构造,每条标注相关 chunk:

| 切片 | 占比 | 示例 |
|---|---|---|
| 语义理解类 | ~40% | "适合带老人小孩的杭州两日游,节奏慢一点" |
| POI 精确名称类 | ~25% | "文和友排队攻略" / "茶颜悦色哪款好喝" |
| 长尾偏好类 | ~20% | "成都本地人去的苍蝇馆子,不要网红店" |
| 口语噪声类 | ~15% | 含错别字、简称、无标点口语表达 |

**标注规范**:

- 相关性三级:2 = 直接回答该查询;1 = 部分相关;0 = 无关。
- 每条查询至少标注全部 2 级相关 chunk(召回评估的 ground truth)。
- 标注人与复核人分离;分歧协商定稿。标注结果存 `docs/05-评估/golden-set/`,JSONL 格式,字段:`query_id`、`query`、`slice`、`relevant_chunk_ids`、`relevance_grades`。

**可执行验收标准**:给定 30 条查询与候选 chunk 池,当标注完成时,则每条查询的 2 级相关 chunk 标注覆盖率 100%,且每条标注经第二人复核。

## 5. 评估指标

**效果指标(主)**:

- Recall@5、Recall@10(以 2 级相关 chunk 为命中)
- MRR@10、nDCG@10(使用三级相关性打分)
- POI 切片单独统计命中率(检验精确匹配能力,这是 BGE-M3 混合方案的预期优势点)

**工程指标(辅)**:

- 查询延迟 p50 / p95(本机环境记录硬件配置)
- 灌库吞吐(chunk/s)与峰值内存
- 索引磁盘占用

**记录要求**:每组实验保留原始检索结果(top-10 chunk ID 列表),便于 bad case 分析与复核。

## 6. 实验流程

1. 准备语料并切分,灌入 chunk registry(Postgres)。
2. 构建查询集并完成标注、复核,golden set 入库。
3. 分别用 A、B、C 三组配置生成向量并灌入 pgvector 三张表。
4. 逐条执行 30 条查询,记录 top-10 结果与延迟。
5. 脚本计算第 5 节全部指标,生成对比表。
6. 人工抽查各组 top-10 中的差异项与明显 bad case,归档 `docs/05-评估/bad-case/`。
7. 按第 7 节判定标准得出结论,撰写评估报告,提交评审。

spike 代码(实验脚本)遵循项目规范:可运行、可复现,但不合入主干;结论固化到文档后再决定工程化去向。

## 7. 判定标准(决策规则)

给定三组实验的指标结果,按以下规则裁决:

1. 当 A 组 Recall@10 领先 B 组 ≥ 2pp,且 C 组相对 A 组在 POI 切片的领先 < 3pp,则选 **Qwen3-Embedding-0.6B(纯稠密)**。
2. 当 A、B 组 Recall@10 差距 < 2pp,且 C 组在 POI 切片领先 A 组 ≥ 3pp,则选 **BGE-M3 混合检索**。
3. 当 C 组混合收益显著但整体差距存疑时,追加「Qwen3-Embedding + tsvector BM25」对照组,以该组与 C 组的对比决定混合检索的实现方式。
4. 任何情况下,当两组效果指标差距均在测量噪声内(Recall@10 差距 < 2pp 且 POI 切片差距 < 3pp),则以工程指标与生态成熟度裁决(运维成本、社区支持、与现有工具链集成度)。

30 条查询的小样本存在方差,关键指标差距在临界值附近时,以人工抽查的 bad case 性质(是否触及核心场景)作为最终裁定依据,并在评估报告中如实记录。

## 8. 环境与成本

| 项 | 估计 |
|---|---|
| 模型下载 | Qwen3-Embedding-0.6B ≈ 1.2 GB,BGE-M3 ≈ 2.1 GB |
| 硬件 | CPU 可跑(灌库分钟级);有 GPU 则扩大语料规模后结论更贴近生产 |
| 依赖 | sentence-transformers / FlagEmbedding、pgvector、numpy |
| 工作量 | 语料与标注约 1~2 人日,脚本与跑批约 1 人日 |

## 9. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 合成语料与真实笔记分布差异导致结论失真 | 选型结论仅以真实语料结果为准;合成语料仅用于跑通流程 |
| 小样本(30 查询)方差大 | 判定标准设噪声带(第 7.4 条);临界情况以 bad case 性质裁定 |
| 小红书内容版权/合规 | 语料仅内部评估用途,不入库分发,不进 prompt 无关上下文 |
| 本机 CPU 延迟数据不代表生产 | 报告中注明硬件环境;延迟仅作组间相对比较,不作绝对 SLA 依据 |

## 10. 产出物与后续衔接

- 本方案评审通过后执行,产出:**评估报告**(含指标对比表、bad case 分析)→ 存 `docs/05-评估/`。
- 选型结论 → 新写 ADR(embedding 模型选型,含背景、选项、理由、备选)→ 存 `docs/02-架构/adr/`。
- golden set 与标注规范 → M5 评估集的首批资产,后续所有 prompt / 模型 / 工具描述变更按规范重跑。
- 实验 spike 脚本 → 不合入主干;若 M5 需要常驻评估流水线,届时按规范重写为正式工程代码。
