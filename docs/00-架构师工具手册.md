# AI 架构师工具与干预手册（trip_agent）

> 状态：草案 | 制定：2026-10-22 | 变更记录见文末

本文档是 [00-项目开发流程规范](00-项目开发流程规范.md) 的配套手册，从 **AI 架构师视角**回答一个问题：

> 在 M0~M7 每个阶段，哪些点必须**人工干预**（用户拍板），哪些点需要**调用工具加强判断**（架构师自行调用）？用哪个工具、怎么用、产出落在哪。

---

## 1. 使用方式与工具分级

**两个原则**：

1. **工具加强判断，不替代判断**。工具产出必须汇入既有文档体系：澄清结论进 `docs/01-需求/`，架构决策进 `docs/02-架构/adr/`，评审结论写入对应文档的状态行。工具不允许产生游离于文档体系之外的"散装产物"。
2. **人工干预点 = 硬门禁**。标 🔴 的干预点未通过，流程不往下走（对应 00 规范的"未定稿不实现"）。

**工具分级**（引入成本从低到高，引入时从低到高逐级评估）：

| 级别 | 定义 | 代表工具 | 引入规则 |
|---|---|---|---|
| **L0** | 本机已装，零成本 | grilling、code-review、code-architecture-review、simplify、dataviz、docx、pdf、claude-api、senior-fullstack、security-review、skill-creator、question-journal、browser-use | 直接调用 |
| **L1** | 生态 skill，一条命令安装 | interview-me、grill-with-docs、write-spec、bmad-prd、pre-mortem | 需要时安装，记录于第 4 节清单 |
| **L2** | MCP server，常驻依赖 | intent-gate-mcp、ai-architect-mcp-spec | 必须写 ADR 且你确认后才引入；当前均为候选暂缓 |
| **L3** | 外部调研手段 | WebSearch / WebFetch / browser-use | 调研结论必须落文档（ADR 或对比表），不留"我记得查过" |

## 2. 各阶段干预点与工具总览

| 阶段 | 🔴 人工干预点（必须你参与） | 工具加强点（我自行调用） | 阶段门禁 |
|---|---|---|---|
| M0 需求定稿 | ① 提供 raw 文档 ② 回答澄清问题 ③ 需求规格定稿签字 ④ 裁决双轮复审遗留问题 | 读文档（L0 docx/pdf）→ 澄清访谈（L0 grilling / L1 interview-me、grill-with-docs）→ 规格成稿（L1 write-spec）→ 对抗评审（L1 pre-mortem、bmad-prd）→ 定稿前双轮复审（附录 A） | 需求规格 = 定稿（双轮复审遗留问题已裁决） |
| M1 架构设计 | 技术选型逐篇 ADR 确认 | 调研（L3 WebSearch/browser-use）→ 决策树（L0 grilling）→ 架构评审（L0 code-architecture-review）→ LLM 集成模式（L0 claude-api） | 架构设计定稿 + ADR 全部确认 |
| M2 项目骨架 | 确认目录与工具链 | 规范对照自查（Glob/Grep）；参考你本机 video-studio 的 FastAPI 分层实践 | pytest / ruff / mypy 全绿 |
| M3 核心闭环 | 演示 + 按验收标准逐条核对 | 实现参考（L0 senior-fullstack、react-nextjs-patterns、frontend-design）；交付前 code-review + simplify（L0） | 验收标准逐条通过 |
| M4 功能迭代 | 逐功能验收；补充领域规则 | 规格压测（L0 grilling）→ 每任务 code-review + simplify（L0）→ 里程碑末 code-architecture-review（L0）防架构腐化 | DoD 清单逐项通过 |
| M5 评估调优 | 提供 bad case 与期望范例；确认评估对比结论 | bad case 归因（L0 grilling）→ 评估报告（L0 dataviz）→ LLM-as-judge 并行评估（多 Agent） | 评估对比通过才允许 prompt 变更合并 |
| M6 发布运维 | 提供部署环境、密钥、域名 | 安全审查（L0 security-review）→ 全量回归（pytest + code-review） | 安全检查清单全过 |
| M7 持续运营与复盘 | 收集使用反馈 | 问题沉淀（L0 question-journal）→ 流程 skill 化（L0 skill-creator）→ 复盘（L0 grilling） | 复盘结论落 ADR |

> 注：00 规范当前定义 M0~M6，M7 为提案阶段（见第 5 节），待你确认后按变更流程补入 00 规范。

## 3. 分阶段详解

### M0 需求定稿

| 场景 | 工具 | 动作与产出 |
|---|---|---|
| a. 读原始需求文档 | L0 `docx` / `pdf` | 读 `docs/01-需求/raw/` 里的原始文档；网页/截图类材料用 `browser-use` 抓取后归档进 raw/ |
| b. 澄清访谈 | L0 `grilling`（首选）| 把需求画成决策树，逐轮只问"前置条件已满足"的问题，每问附推荐答案；产出 → `01-需求/澄清问题清单.md` |
| b'. 深度意图探测 | L1 `interview-me` | 当发现用户说"应该做 X"但语气像套话（"可扩展""最佳实践"）时启用，探测 want vs. should-want，置信度 ≥95% 才算问完 |
| b''. 落盘式访谈 | L1 `grill-with-docs` | 澄清过程中术语实时写 GLOSSARY.md，满足门槛的决策直接生成 ADR 种子（进 `02-架构/adr/` 待 M1 评审） |
| c. 规格成稿 | L1 `write-spec`（Anthropic 官方）| 以澄清结论为输入，生成 P0/P1/P2 需求 + 验收标准骨架，再按《需求规格》模板补齐 → `01-需求/需求规格.md` |
| d. 对抗评审 | L1 `pre-mortem` + L1 `bmad-prd`（Validate 模式）| 预演"这个需求上线一年后失败的样子"；按 7 维 rubric 打分（决策就绪度、范围诚实性、验收可测性…），发现的问题回写澄清清单 |
| e. 定稿前双轮复审 | 独立会话提示词模板（附录 A，免安装）；可选 L1 `requirements-reviewer` / `review-spec` | **轮次一**（新会话）：单文档质量审查——模糊表述、前后矛盾、AC 可测性、缺失业务规则；**轮次二**（另一新会话）：跨文档一致性复核——修订残留、承诺丢失、术语漂移。两轮均只读、引用原文；产出问题清单 → 你逐条裁决 → 按变更流程修订《需求规格》并记《变更记录》 |

**🔴 门禁**：你确认《需求规格》定稿。任何"挺好的""先这样吧"不算确认，需要明确同意（对应 interview-me 的确认纪律）。定稿前置：附录 A 双轮复审已执行，阻塞/高严重度问题已修复或经你显式豁免。

### M1 架构设计

| 场景 | 工具 | 动作与产出 |
|---|---|---|
| a. 技术选型调研 | L3 `WebSearch` / `WebFetch` + L0 `browser-use` | 框架对比必须覆盖：版本活跃度、许可证、与你本机技术栈的匹配度；结论写成 ADR（含备选方案与放弃理由），不允许"我查过了"式的口头结论 |
| b. 架构决策树 | L0 `grilling` | 把未决架构问题全部暴露：Agent 编排框架、记忆方案、流式、数据库、可观测性……逐轮决策，每轮附推荐答案 |
| c. 架构文档评审 | L0 `code-architecture-review` | 对《架构设计》文档做对抗式评审（模块边界、依赖方向、扩展点、失败模式）；发现的问题回 ADR |
| d. LLM 集成模式 | L0 `claude-api` | 设计 `llm/` 层时查工具调用、流式、结构化输出的当前最佳实践，保证与所选模型 API 对齐 |

**🔴 门禁**：ADR 逐篇经你确认（草案 → 定稿）。M1 结束后架构设计不得"先斩后奏"变更。

### M2 项目骨架

| 场景 | 工具 | 动作与产出 |
|---|---|---|
| a. 规范对照自查 | 内置 Glob/Grep | 逐条核对目录结构与 00 规范第 6 节一致；工具链配置（ruff/mypy/pytest）跑通 |
| b. 借鉴已有实践 | 内置 Read | 参考你本机 video-studio backend 的 FastAPI 分层写法——只借鉴好约定，不照搬其未文档化的临时做法 |

**🔴 门禁**：你确认目录与工具链（无异议可默认通过）。

### M3 核心闭环（walking skeleton）

| 场景 | 工具 | 动作与产出 |
|---|---|---|
| a. 全栈实现参考 | L0 `senior-fullstack`；前端若选 React → `react-nextjs-patterns`、`vercel-react-best-practices`；视觉规范 → `frontend-design`、`web-design-guidelines` | 保证切片代码质量基线，不把坏味道带进后续迭代 |
| b. 流式/工具调用 | L0 `claude-api` | Agent 调用链实现对照 |
| c. 交付前评审 | L0 `code-review` + `simplify` | 切片进 main 前必跑 |

**🔴 门禁**：演示 + 验收标准逐条核对；你的现场反馈写入 `01-需求/变更记录.md`。

### M4 功能迭代

每个功能走五步（任务规格 → 实现 → 测试 → 自审 → 交付），工具内嵌如下：

| 步骤 | 工具 | 说明 |
|---|---|---|
| 规格评审 | L0 `grilling` | 任务规格含歧义时压测（范围边界、异常路径、验收可测性） |
| 自审 | L0 `code-review` + `simplify` | 每任务交付前必跑 |
| 里程碑末 | L0 `code-architecture-review` | 防架构腐化：检查依赖方向、分层泄漏（如 tools 反向依赖 agents）、prompt 散落 |

**🔴 门禁**：逐功能验收 + DoD 清单。若出现"为了赶进度绕过门禁写码"的苗头 → 触发 L2 候选 `intent-gate-mcp` 的引入评估（写 ADR）。

### M5 评估调优

| 场景 | 工具 | 动作与产出 |
|---|---|---|
| a. golden set 构建 | 内置 Agent（并行） | 从《需求规格》的验收标准反推 golden case（输入、期望要点、评分维度），落 `docs/05-评估/` |
| b. bad case 归因 | L0 `grilling` | 逼问真实期望，归因到 prompt / 工具描述 / 模型能力三层，避免"就是不够聪明"式结论 |
| c. 评估报告 | L0 `dataviz` | 评分对比、回归可视化，报告落 `docs/05-评估/` |
| d. 批量评估 | 多 Agent 并行（LLM-as-judge） | 大规模跑评估集时并行评分，评委 prompt 与主 prompt 分文件管理 |

**🔴 门禁**：你确认评估对比结论；prompt/模型变更合并以评估对比通过为前提（00 规范第 8 节）。

### M6 发布运维

| 场景 | 工具 | 动作与产出 |
|---|---|---|
| a. 安全审查 | L0 `security-review` | 重点：prompt injection 面、密钥管理、依赖漏洞、PII 脱敏是否落实 00 规范第 8.7 条 |
| b. 全量回归 | pytest + L0 `code-review` | 上线前全量回归 |

**🔴 门禁**：安全检查清单全过；部署信息由你提供。

### M7 持续运营与复盘（提案阶段）

| 场景 | 工具 | 动作与产出 |
|---|---|---|
| a. 问题沉淀 | L0 `question-journal` | 把项目过程中你的问题归档，形成个人学习资产 |
| b. 流程 skill 化 | L0 `skill-creator` | 把成熟的工作流（如"任务五步走"）沉淀成项目级 skill，降低后续会话的规范执行成本 |
| c. 阶段复盘 | L0 `grilling` | 对里程碑复盘（哪些决策事后证明错了），结论更新 ADR |

**🔴 门禁**：你确认 M7 是否正式纳入 00 规范（见第 5 节）。

## 附录 A：M0 需求规格双轮复审提示词模板

《需求规格》多轮修订后，定稿前执行一次双轮复审，作为 M0 门禁（见 §3 M0-e）的固定动作。

**四条纪律**：

1. **每轮各用一个新会话**，两轮互不带结论（避免第一轮判断锚定第二轮）。不要用 `/fork`——fork 复制全部会话历史，既不独立也不省上下文。
2. **只读**：复审只产出问题清单，不修改任何文档；修改发生在裁决之后，走 00 规范变更流程。
3. **引用原文**：每项发现必须给出文件 + 章节 + 原文引用，禁止"感觉这里不清楚"式的无定位发现。
4. **区分两类发现**：【文档缺陷】（矛盾、不可测试、残留旧表述，可直接修）与【开放问题】（业务取舍，必须由你裁决，AI 不得猜测业务答案）。

**轮次一：单文档质量审查**（新会话发送）：

```text
你是资深需求工程师。请对 docs/01-需求/需求规格.md 做一次只读质量审查,不要修改任何文件。

背景:这是「智能旅行助手」项目的 M0 需求规格,当前状态为"评审中"。项目规范要求验收标准必须是可执行的"给定X,当Y,则Z"形式。

请重点检查:
1. 模糊或不可测试的表述(如"合理""及时""良好体验"等未量化措辞)
2. 前后矛盾:同一事项在不同章节(功能清单/输入规格/验收标准/非功能需求/§9评审记录)的不一致
3. 缺失的业务规则:异常流程、边界值、空状态、权限、并发等未覆盖的场景
4. 验收标准缺陷:AC 无法执行验证、缺少前置条件、与功能清单(F1-F16)不能一一对应
5. 未量化的非功能需求
6. 术语不一致(同一概念多种叫法)

要求:
- 每项发现必须引用原文和所在章节
- 区分两类:【文档缺陷】(可直接修)和【开放问题】(需要我来裁决,禁止替我猜测业务答案)
- 按严重程度排序(阻塞/高/中/低)
- 输出格式:位置|原文引用|问题类型|下游风险|严重度|最小修改建议或待裁决问题
- 先穷尽式扫描,再过滤报告;不要只做抽查
```

**轮次二：跨文档一致性复核**（另开新会话发送）：

```text
请对以下文档做跨文档一致性复核,只读,不修改任何文件:
- docs/01-需求/需求规格.md
- docs/01-需求/澄清问题清单.md
- docs/01-需求/变更记录.md
- docs/01-需求/raw/业务需求文档-v0.md

背景:需求规格经过多轮 Q/RP 决议修订(变更记录有 20+ 条),我担心修订后有残留的旧表述或未同步的连带影响。

请检查:
1. 相互矛盾:不同文档对同一事项的描述冲突
2. 修订残留:变更记录中已决议修订的内容,在需求规格正文中仍有旧版本表述
3. 承诺丢失:原始需求文档(raw)中的功能点,在需求规格中既未纳入也未明确排除
4. 术语漂移:同一实体在不同文档中的命名不一致
5. 连带遗漏:某项决议(如 Q19 预算口径、Q21 消费档位)应联动的章节未同步更新

要求:
- 每项发现给出具体文件+章节+原文引用
- 给出最小的一致性修复建议,不评判产品决策本身
- 按严重程度排序输出
```

**结果处理**：两轮完成后合并去重 → **使用 AskUserQuestion 工具逐条向你确认**（每条发现一问：采纳修改 / 不采纳 / 豁免并记原因 / 推迟到二期；互不依赖的发现可每批最多 4 条合并提问）→ 仅对确认采纳的项，按变更流程修订《需求规格》并同步《变更记录》→ 阻塞/高严重度清零或显式豁免后方可定稿。只跑一轮时优先轮次一。未获确认的项一律不改，记录为"已评审未采纳"留痕。
