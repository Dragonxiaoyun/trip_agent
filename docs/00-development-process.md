## 2. 核心开发原则(不可妥协)

1. **文档先行,代码后到**:任何模块在写代码前,必须有对应的已评审文档(需求 → 设计 → 任务拆解)。没有文档的代码一律视为探针(spike),不得合入主干。
2. **小步快走,阶段门禁(Stage Gate)**:项目划分为若干阶段,每个阶段有明确的入口条件、交付物和验收标准。上一阶段未验收,不进入下一阶段。
3. **AI 生成 ≠ 免责**:所有 AI 产出的代码和文档,人类必须评审。AI 对每一处设计决策必须给出理由和备选方案,不允许"黑盒交付"。
4. **架构决策可追溯**:重要技术选型写入 ADR(架构决策记录),说明背景、选项、决策、后果。禁止口头决策。
5. **契约优先**:模块间先定义接口/数据契约(Pydantic schema、OpenAPI、TypeScript 类型),再实现。Agent 的 Prompt、工具定义、状态结构都属于契约,纳入版本管理。
6. **质量内建**:测试、类型检查、Lint 不是最后补的,是每个任务的完成定义(DoD)的一部分。

## 3. 开发流程总览(阶段门禁模型)

```
阶段0 立项        阶段1 需求       阶段2 架构设计     阶段3 模块开发      阶段4 集成联调     阶段5 上线准备
──────────►     ──────────►     ───────────►     ───────────►     ───────────►     ───────────►
项目章程          PRD 定稿        架构设计文档         可运行增量          端到端可用          生产就绪
技术可行性        用户旅程         ADR 定稿           单测通过            联调通过            监控告警就绪
本规范定稿        验收标准         接口契约冻结        Code Review       性能/成本评估      发布清单
```

### 各阶段详表

| 阶段 | 入口条件 | 关键活动 | 交付物(验收物) | 出口标准(Gate) |
|---|---|---|---|---|
| **0 立项** | 有初步想法 | 明确目标用户、核心场景、边界;技术可行性预研;制定本规范 | `01-project-charter.md`、本规范 | 人类确认章程和规范 |
| **1 需求** | 阶段0验收 | 业务需求文档结构化;用户旅程;功能优先级(P0/P1/P2);非功能需求(性能/成本/安全) | `10-prd.md`、用户旅程图、验收标准清单 | PRD 评审通过,需求冻结(变更走变更流程) |
| **2 架构设计** | PRD 冻结 | 系统上下文图、模块划分、Agent 编排设计(LangGraph 状态图)、数据模型、API 契约、技术选型 ADR、非功能设计(缓存/限流/成本) | `20-architecture.md`、`2x-adr-*.md`、`contracts/`(OpenAPI + Pydantic schema) | 架构评审通过;契约冻结 |
| **3 模块开发** | 契约冻结 | 按任务卡(Task Card)逐个模块实现;每个任务:设计要点 → 代码 → 测试 → Review | 可运行代码 + 单测 + 任务卡归档 | 每个任务卡满足 DoD(见 §7) |

## 4. 你与 AI 的协作方式:每一步提供什么

这是你最关心的问题。每一轮沟通,你提供"输入",我交付"产出",双方确认后进入下一步。

| 步骤 | 你需要提供给我 | 我交付给你 | 确认方式 |
|---|---|---|---|
| 0. 立项(当前) | ① 业务需求文档原文 ② 简单设计文档原文 ③ 三个补充信息:目标用户是谁、首个版本最想跑通的一个场景、预算/成本约束(用哪家 LLM、月成本上限) | 项目章程草案、可行性风险清单 | 你回复"确认"或修改意见 |
| 1. 需求 | ① 对 PRD 草案的优先级判断(哪些必须有、哪些可以砍) ② 真实的用户需求细节(你设想的用户使用方式) | 结构化 PRD、用户旅程、验收标准 | PRD 评审会(逐条过) |
| 2. 架构 | ① 对我提出的 2-3 个架构方案做选择 ② 你已有的技术资产/偏好(如已有云账号、数据库偏好) | 架构设计文档、ADR、接口契约 | 逐 ADR 确认 |
| 3. 开发 | ① 每个任务卡完成后你的 Review 意见 ② 真实 API Key 等环境资源 | 可运行代码、测试、每个决策的说明 | 任务卡验收(跑通 + 测试绿) |
| 4. 联调 | ① 真实场景的测试用例(你会怎么用这个产品) ② 对 Agent 输出质量的主观评价 | 联调报告、评测结果、问题清单 | 核心旅程走通确认 |
| 5. 上线 | ① 部署目标环境信息 ② 域名/账号等资源 | 部署文档、Runbook | 发布检查单签字 |

**沟通规则**:
- 每次我向你索取信息时,会明确列出"为什么需要、缺了会有什么风险"。
- 你可以随时说"跳过,按推荐方案来",我会选择默认方案并在文档中标记为"待确认决策"。
- 每完成一个阶段,我会输出一份**阶段小结**:做了什么、哪些决策已冻结、哪些待办遗留。

### 5.2 文档规则

- 所有文档用 Markdown,中文撰写,代码标识符保持英文。
- 每份文档头部有元信息:版本、状态(草案/评审中/已冻结)、作者、日期。
- **已冻结**的文档修改必须升版本号并在文末记录变更历史。
- ADR 一旦Accepted不得修改内容,只能被新的 ADR 标记为"已被 XXX 取代"。

## 6. 代码与目录规范

### 6.1 仓库目录结构(后端,阶段2定稿后冻结)

```
trip_agent/
├── docs/                        # 见 §5
├── backend/
│   ├── pyproject.toml           # 依赖与工具配置(uv/pip 管理)
│   ├── src/trip_agent/
│   │   ├── main.py              # FastAPI 入口,只做装配
│   │   ├── config/              # 配置管理(pydantic-settings,环境分层)
│   │   ├── api/                 # HTTP 层:路由、请求/响应模型,不含业务逻辑
│   │   ├── agents/              # Agent 层:LangGraph 图定义、节点、状态
│   │   │   ├── graphs/          # 图定义(每个 Agent 一张图)
│   │   │   ├── nodes/           # 节点函数
│   │   │   ├── tools/           # 工具定义(搜索、天气、地图、酒店...)
│   │   │   └── prompts/         # Prompt 模板(纳入版本管理,禁止散落在代码里)
│   │   ├── services/            # 业务服务层:编排 Agent 调用、业务规则
│   │   ├── domain/              # 领域模型(Pydantic,纯数据结构,无 IO)
│   │   ├── infrastructure/      # 外部依赖:DB、缓存、第三方 API 客户端
│   │   └── core/                # 横切:日志、异常、中间件、鉴权
│   └── tests/
│       ├── unit/                # 单元测试(不访问外部服务,LLM 全部 mock)
│       ├── integration/         # 集成测试(真实 DB / 第三方 API,CI 可选)
│       └── evals/               # Agent 评测集(黄金用例 + 评分脚本)
├── frontend/                    # 二期初始化,Next.js
├── scripts/                     # 开发脚本(seed、数据迁移、评测运行器)
└── AGENTS.md                    # 给 AI 协作者的项目宪法(指向本规范)
```

### 6.2 分层依赖规则(强制)

```
api → services → agents → domain
                  ↓
           infrastructure
```

- 依赖只能向下,**禁止反向依赖**(如 domain 不得 import infrastructure)。
- `api` 层只做协议转换,业务逻辑必须下沉到 `services`。
- 所有外部 IO(LLM、HTTP、DB)只能出现在 `infrastructure` 和 `tools` 中,便于 mock 和替换。

### 6.3 编码规范

- **风格**:Ruff(lint + format)统一管控,行宽 100;类型注解全覆盖,mypy strict 模式。
- **命名**:文件/模块 `snake_case`,类 `PascalCase`,函数变量 `snake_case`,常量 `UPPER_SNAKE`。
- **注释原则**:只写"为什么",不写"是什么";Prompt 模板必须带注释说明设计意图和已知坑。
- **错误处理**:不允许裸 `except`;外部调用必须有超时和重试(指数退避);所有异常最终映射为统一 API 错误格式。
- **LLM 调用铁律**:
  1. 任何 LLM 调用必须可配置模型名/温度等参数,禁止硬编码。
  2. 结构化输出一律用 Pydantic 输出解析,禁止裸字符串解析 JSON。
  3. Prompt 模板文件化,变量显式声明,禁止 f-string 拼接用户输入进 Prompt。
  4. 每次调用必须接入 LangSmith tracing(开发环境)以便调试和成本统计。
- **密钥**:只走环境变量 + `.env`(gitignore),代码库中不得出现任何密钥,提交前 gitleaks 检查。

### 6.4 前端规范(占位,二期细化)

Next.js App Router / TypeScript strict / 组件按 feature 目录组织 / 服务端状态用 TanStack Query。

## 7. 任务卡与完成定义(DoD)

### 7.1 任务卡模板(每个开发任务一张,存 `docs/tasks/`)

```markdown
# TASK-XXX: <任务名>
- 来源:PRD §x.x / 架构文档 §x.x
- 契约依赖:<涉及的 schema/API>
- 设计要点:<实现思路,3-5 条>
- 验收标准:<可执行、可验证的条件>
- 状态:待开发 / 开发中 / 待评审 / 已完成
```

### 7.2 完成定义(Definition of Done)

一个任务只有同时满足以下条件才算完成:

- [ ] 代码通过 `ruff check` + `ruff format --check` + `mypy`
- [ ] 新增逻辑有单元测试,覆盖率不拉低整体(目标 ≥ 80%)
- [ ] 涉及 Agent 行为的变更,评测集(`tests/evals/`)核心用例不回归
- [ ] 接口/契约变更已同步更新 `docs/contracts/` 并标注版本
- [ ] 人类评审通过

## 8. Git 与版本规范

- **分支模型**:简化的 trunk-based。`main` 始终可发布;功能分支 `feat/TASK-001-xxx`,修复 `fix/xxx`,生命周期 ≤ 3 天。
- **提交信息**:Conventional Commits —— `feat(agents): add itinerary planner node`、`fix(tools): handle weather API timeout`。
- **合并要求**:小步合并,每次 PR 对应一个任务卡;PR 描述必须链接任务卡并写明"如何验证"。
- **禁止**:`git push --force` 到 main、跳过 CI 合并、把 `.env` 或密钥提交进库。

## 9. 质量与测试策略

| 层级 | 内容 | 工具 | 何时跑 |
|---|---|---|---|
| 静态检查 | Lint、格式、类型 | Ruff、mypy | 每次提交(pre-commit) |
| 单元测试 | 纯逻辑、工具函数、图节点(mock LLM) | pytest | 每次提交 |
| 集成测试 | DB、第三方 API(沙箱) | pytest + 标记 | CI / 按需 |
| **Agent 评测** | 黄金用例集:给定输入,评估 Agent 输出质量(正确性/格式/工具选择) | pytest + LangSmith evaluate | Agent 变更时 + 每晚 |
| 端到端 | 核心用户旅程全链路 | playwright / API 测试 | 阶段4 |

> Agent 应用的测试难点在于"输出不确定",因此评测集是本项目测试体系的核心,阶段1就要确定第一批黄金用例。
