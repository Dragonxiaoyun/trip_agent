M1 架构选型 · 前端框架对比

同一次访问，
两条截然不同的渲染路径与命运

React + Vite 与 Next.js 用的是同一个 React。区别不在语法，在于：页面在哪里被渲染、用户何时能看到内容。下面两条流水线把这件事画出来。

PART 1

渲染流水线：从请求到画面

跟随一次页面访问走完全程。注意每个步骤发生在 服务器 还是 浏览器，以及底部时间轴上"白屏期"的长度差异。

React + Vite
CSR · 客户端渲染

服务器只发一个"空壳"，所有渲染工作都在用户的浏览器里完成。

1
浏览器请求页面 浏览器
用户输入网址，发出第一个请求
2
返回空 HTML + script 标签 服务器
HTML 里几乎没有任何内容，只有一个 JS 入口
3
下载并执行 JS bundle 浏览器
React + React Router + 状态库…几百 KB 起，白屏等待
4
React 渲染出页面骨架 浏览器
出现 loading 占位，但还没有真实数据
5
再发请求取数据 浏览器
调用后端 API（如 FastAPI），又一次网络往返
6
内容真正可见、可交互 浏览器
至此用户才看到完整页面
TIME →用户视角
白屏 / loading（步骤 1–5）
内容渲染
可交互

首屏慢：内容可见前要经历 2 次网络往返 + 一次完整 JS 执行。搜索引擎爬虫看到的也基本是空壳，SEO 天然吃亏。

Next.js
SSR / 流式渲染

服务器先把页面渲染好，浏览器收到的第一口 HTML 就是带内容的。

1
浏览器请求页面 浏览器
同样从一个请求开始
2
服务器取数据 + 渲染 HTML 服务器
数据获取发生在服务器内网，通常更快、更安全
3
HTML 流式返回，内容直接可见 → 浏览器
Suspense 让页面分块"流"出来：先出框架，数据好的区块随到随显
4
后台水合（Hydration） 浏览器
JS 接管页面事件，页面从"能看"变成"能点"
TIME →用户视角
服务器渲染
内容可见（边流边显）
水合可交互

首屏快：用户看到的是真实 HTML 而非 loading；爬虫同样拿到完整内容，SEO 开箱即用。流式渲染对 LLM 长输出场景尤其友好。

PART 3

决策流程：你的项目该选哪个

三个问题，按顺序回答，走到终点就是答案。

Q1 · 有面向公众的页面，需要被搜索引擎收录吗？ 例如：行程分享页、目的地攻略落地页、营销官网
是 YES
Next.js SEO 是硬需求，CSR 补救成本高，直接定案
否 NO
Q2 · 有 LLM 长输出，需要边生成边展示吗？ 例如：几十秒的行程生成过程逐块浮现，而不是 loading 转圈
是 YES
Next.js 流式渲染 + AI SDK 省掉大量手工流处理
否 NO
Q3 · 登录后使用的工具型应用，追求前后端极简分离？ 已有 FastAPI 后端，前端只是纯 SPA 工作台
是 YES
React + Vite 静态产物任意部署，架构最简单
不确定
Next.js 能力超集更大，给未来留空间
VERDICT · trip_agent 智能旅行助手

推荐 Next.js

  • Q1 = 是：行程分享页 / 攻略落地页是天然获客入口，需要 SEO 与快首屏
  • Q2 = 是：行程规划是 LLM 长输出，流式渲染让"交通→酒店→景点"逐块浮现
  • 大量景点/酒店图片：内置图片优化开箱即用，Vite 方案要自己搭
  • 注意：FastAPI 仍是唯一后端，Next.js API 路由只做轻量 BFF 代理，不写业务逻辑
