## 1. 地图与位置服务

### POI(Point of Interest,兴趣点)

地图上有名称、有坐标、值得被标注出来的一个地点实体，如一家餐厅、一座地铁站、一个景点。

**第一性原理推导**：计算机无法理解"故宫"这种人类概念，只能处理数据。要让机器帮用户找路、找餐厅，必须把物理地点数字化。描述一个地点，最少需要：**坐标**(它在哪)+ **名称**(它叫什么)+ **类别**(它是什么——餐厅还是加油站，决定了对用户有没有用)；再叠加**属性**(营业时间、电话、人均消费、评分)才有实用价值。因此 POI 的本质是：**把物理世界中一个有意义的地点，抽象为"坐标 + 名称 + 类别 + 属性"的结构化数据记录**，是现实空间与数字服务之间的最小映射单元——导航、搜索、周边推荐、打车、外卖全部建立在这层抽象之上。

**本项目中的角色**：景点标注(AC-5)、餐饮代表店的评分/人均(AC-16)、酒店与景点的坐标均来自高德 POI 查询，**不允许 LLM 编造坐标**。关键字搜索个人免费配额 5,000 次/月偏紧，故架构要求 POI 结果缓存(同一景点只查一次，见 RP-3)。

**一条高德 POI 数据(简化)**:

```json
{
  "id": "B000A83M61",
  "name": "故宫博物院",
  "type": "风景名胜;公园广场;世界遗产",
  "location": "116.403414,39.924091",
  "address": "北京市东城区景山前街4号",
  "tel": "010-85007421",
  "rating": "4.8",
  "cost": "60.0"
}
```

### 地理编码 / 逆地理编码(Geocoding / Reverse Geocoding)

- **地理编码**：把文字地址/地名转换成经纬度坐标（"故宫博物院" → `116.403414,39.924091`）。
- **逆地理编码**：把经纬度坐标转换成文字地址（地图上点一个点 → 告诉你这是哪条街）。

### GCJ-02 / WGS-84(坐标系)

两套经纬度坐标标准。**WGS-84** 是 GPS 全球通用坐标系；**GCJ-02**(俗称"火星坐标")是中国大陆强制使用的加密偏移坐标系，国内地图(高德/腾讯/百度部分产品)均使用它。同一地点在两套坐标下数值不同，**跨国数据混用必须转换**(本项目在地图 provider 层处理，见 RP-3/RP-4)。

### 审图号

中国对公开发行的地图实行的行政审批编号。中国境内发布地图须由持测绘资质单位提供并附审图号，这是国内场景只能用高德/腾讯/百度等国内图商、不能用 Google Maps 的合规根因(见 RP-3)。

### 路径规划(Route Planning)

地图服务商提供的 API 能力：给定起点/终点坐标与出行方式(驾车/公交/步行/骑行),返回距离、耗时与路线。**本项目硬性要求**：当地交通的段间距离/耗时必须来自高德路径规划 API(AC-21),自驾方案里程/耗时必须来自高德驾车路径规划 API(AC-24),不得由 LLM 估算编造。

### 地图 provider 接口

本项目架构抽象：把"地理编码/POI 搜索/路径规划/静态图"等地图能力定义成统一接口(provider),高德、腾讯、Mapbox 都是该接口的不同实现，便于按国内/国外场景切换与降级(RP-3 决议)。

## 2. LLM 与 Agent

### LLM(Large Language Model,大语言模型)

如 DeepSeek、GPT 等，通过自然语言交互完成推理、生成、总结的模型。本项目中 LLM 负责理解用户输入、编排工具调用、生成行程文案，但**不负责精确计算**(预算加总由 calculator 工具完成)和**事实性数据**(坐标/距离/实时价格一律来自工具查询)。

### Agent(智能体)

以 LLM 为"大脑",能自主规划步骤、调用工具(搜索/天气/地图)、根据工具返回继续行动的程序。与普通"一问一答"的区别：Agent 是**多轮循环**——思考 → 调工具 → 看结果 → 再思考，直到任务完成。

### 工具调用(Tool Calling / Function Calling)

LLM 输出结构化请求("请调用天气工具，参数：城市=北京、日期=10-01"),由代码真正执行 API 调用并把结果喂回给 LLM。本项目的天气、POI、路径规划、calculator 都是工具；每个工具必须有名称、功能描述、参数 schema、返回 schema、副作用声明(见 AGENTS.md 铁律 6)。

### MCP(Model Context Protocol)

Anthropic 提出的开放协议，统一"LLM/Agent 如何连接外部工具与数据源"的接口标准。类比：**USB 接口之于外设**——工具方按 MCP 标准实现一次，任何支持 MCP 的 Agent 都能即插即用。本项目的飞常准(票务)、RollingGo(酒店)、美团、博查(搜索)均以 MCP 服务形式接入(见 RP-1/RP-5/RP-6)。

### LangChain / LangGraph

Python 的 LLM 应用开发框架。LangChain 提供模型调用、工具封装等基础组件；**LangGraph** 是其上的编排层，用"图"(节点=步骤，边=流转条件)描述多步骤 Agent 流程。本项目用它编排行程生成的多阶段流水线(AGENTS.md 技术栈)。

### Prompt(提示词)

发给 LLM 的指令文本，决定模型行为。本项目铁律"Prompt 即代码":全部集中放 `agents/prompts/`,一文件一 prompt,纳入版本管理；涉 prompt 的变更必须重跑评估集。

### Token

LLM 处理文本的最小计费/计量单位，约等于一个汉字或一个英文单词的一部分。每次调用记录 token 用量用于成本统计(规范要求)。

### 结构化输出 / Pydantic 校验

要求 LLM 按预定 JSON 格式输出，并用 Pydantic(Python 数据校验库)定义 schema 强制校验：校验失败 → 带错误信息重试(≤2 次)→ 仍失败则降级兜底，脏数据绝不传给下游(AGENTS.md 铁律 2)。

### 降级(Degradation / Fallback)

首选能力失败时的退路预案，层层退守：实时查询失败 → 区间估算并标注"估算仅供参考"(AC-10/AC-11/AC-12);LLM 全链路失败 → 展示已完成的部分结果 + 明示缺失 + 重试入口，**不得直接报错给用户**。

### 指数退避重试(Exponential Backoff)

调用失败后的重试策略：等待时间按 1s、2s、4s…指数级拉长，避免把故障中的服务打挂。LLM 超时/限流按此策略重试 ≤2 次后进入降级。

### Embedding(向量嵌入)

把一段文本转成一串数字向量，使"语义相近的文本在向量空间距离也相近",是语义检索的基础技术。本项目用于小红书知识库的相似内容检索(见 `docs/05-评估/embedding-选型实验方案.md`、ADR-0002)。

### RAG(Retrieval-Augmented Generation,检索增强生成)

"先检索、再生成":LLM 回答前，先从知识库检索相关内容塞进上下文，让回答基于真实资料而非模型记忆。本项目小红书知识库(攻略/餐厅/经验)按此模式供 Agent 查阅(RP-5)。

### Golden Set(黄金评估集)

一组带标准答案/评分细则的测试用例，用于客观衡量 Agent 输出质量。prompt、工具描述、模型参数变更后必须重跑 golden set 并记录对比结果(规范 DoD)。

## 3. 架构与工程

### ADR(Architecture Decision Record,架构决策记录)

记录重要技术决策的文档：背景、候选选项、决策、理由、备选方案。定稿后只追加不修改，推翻旧决策须新写 ADR。存于 `docs/02-架构/adr/`,如 ADR-0001(前端框架选型)。

### MVP(Minimum Viable Product,最小可行产品)

以最小功能集合验证产品价值的第一个可用版本。本项目 MVP 范围见需求规格 §4 的 P0/P1 功能(F1–F11),F12–F15 为二期。

### API(Application Programming Interface)

程序之间互相调用的约定接口。本项目大量使用第三方 Web API(高德、和风天气)与自建 HTTP API(FastAPI 后端对前端)。

### QPS(Queries Per Second)

接口每秒允许的请求次数上限，是 API 配额的核心维度之一(如高德驾车路径规划个人档 QPS 3)。

### BFF(Backend for Frontend)

专为前端服务的薄后端层，只做请求聚合/转发/鉴权，不写业务逻辑。本项目 Next.js 的 API 路由被限定为 BFF,业务逻辑全部在 FastAPI(见 ADR-0001)。

### CSR / SSR / SSG / SPA(前端渲染方式)

- **CSR**(客户端渲染)：服务器发空壳 HTML,浏览器下载执行 JS 后才渲染内容。首屏慢、SEO 差。
- **SSR**(服务端渲染)：服务器直接生成含内容的 HTML 返回。首屏快、SEO 好。
- **SSG**(静态站点生成)：构建期预生成 HTML,适合内容不变的页面。
- **SPA**(单页应用)：整个应用一个页面，交互靠 JS 局部更新，体验流畅但首屏依赖 CSR。

本项目：公开分享页用 SSR/SSG,登录后工作台用 Client Component(SPA 体验),共存于同一 Next.js 应用(ADR-0001)。

### SSE(Server-Sent Events)

服务器向浏览器单向持续推送数据的协议。用于行程生成的流式进度展示("正在查询天气…正在规划路线…",F9/AC-7)。

### P90

百分位延迟指标：100 次请求按耗时排序，第 90 名的值。"生成耗时 ≤ 90 秒(P90)"意为 90% 的请求在 90 秒内完成(AC-19),比平均值更能反映大多数用户体验。

### Spike(探针)

为验证某个技术可行性而写的一次性试验代码。规范规定：探针代码**不得合入主干**。

### DoD(Definition of Done,完成定义)

交付前必须逐项通过的质量门禁：`pytest` 全绿、`ruff check`、`ruff format`、`mypy --strict`,涉 AI 行为变更还须重跑评估集(见 AGENTS.md)。

## 4. 业务与数据合作

### OTA(Online Travel Agency,在线旅游平台)

携程、飞猪、同程等在线卖机票/酒店/门票的平台。本项目不与其直连预订，只跳转官方渠道。

### CPS(Cost Per Sale,按成交付费)

一种联盟分销模式：平台挂带追踪参数的跳转链接，用户去官方渠道成交后，平台获得佣金(如携程联盟佣金 2-4%)。对应本项目二期功能 F14。

### GDS(Global Distribution System,全球分销系统)

航司机票库存的全球批发分销网络(如 Amadeus、Sabre),机票代理出票的底层系统。个人开发者无出票资质，这是本项目不做站内票务预订的根因之一(RP-2)。

### 飞常准 / RollingGo(本项目已选数据源)

- **飞常准·飞友 AI 开放平台**:以 MCP 协议提供机票实时价格、火车票时刻/余票/票价查询，按调用计费(RP-1 决议选用)。
- **RollingGo**(道旅 DIDA):以 MCP 协议提供全球 200 万+ 酒店实时价格/库存与预订跳转链接，当前免费(RP-6 决议选用)。

### 小红书半自动知识库

本项目的内容补充方案：开发期用 OpenCLI 复用人工已登录会话采集小红书高赞旅行笔记 → LLM 提炼结构化条目 → 人工审核入库；产品运行时只读知识库，**不实时访问小红书**(合规与稳定性约束，RP-5 决议),按季度重采保鲜。
