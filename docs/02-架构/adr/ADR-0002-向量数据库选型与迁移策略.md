# ADR-0002 向量数据库选型与迁移策略：pgvector 起步，预留向 Qdrant/Milvus 的平滑迁移路径

> 状态：草案 · 最后更新：2026-10-28

## 背景

trip_agent 需要构建旅行攻略知识库（RAG），原始语料以小红书攻略笔记为主，支撑行程规划时的景点/餐饮/攻略检索。检索负载的特征：

1. **规模**：初期数万~数十万 chunk，中期预估百万级，远期不超过千万级。
2. **查询模式**：语义检索 + 元数据过滤（城市、主题、POI 类型）混合；攻略中大量 POI 名称、店名，对精确匹配敏感，需要混合检索（向量 + 关键词）。
3. **团队约束**：主库已确定 PostgreSQL，初期无专职运维，组件越少越好。

embedding 模型选型（Qwen3-Embedding-0.6B vs BGE-M3）由 `docs/05-评估/embedding-选型实验方案.md` 定义的实验裁决，不在本文范围。本文决策向量库的选型与后续迁移策略。

## 决策

**初期使用 pgvector（PostgreSQL 扩展）作为向量存储，并在架构上按"可平滑迁移"设计；当规模或性能触及退出条件时，迁移至 Qdrant（首选）或 Milvus（超大规模）。**

架构约束（可迁移性设计，M2 落地时必须遵守）：

- **Chunk registry 独立于向量库**：chunk 原文、元数据（笔记 ID、城市、主题、来源）、`embedding_model_version`、向量维度全部存 Postgres，作为唯一事实来源；任何向量库都可从 registry 重建。
- **检索走抽象层**：业务代码不直接写 pgvector SQL 或任何向量库 SDK，统一走 services 层的 VectorStore 接口，后端实现可配置切换。
- **灌库任务幂等、可断点续传**：一次写好，迁移回填时直接复用。
- **混合检索**：pg 阶段用 `tsvector` 做关键词通道；迁移后改用目标库的稀疏向量/BM25 能力。

退出条件（触发迁移评估，满足其一即启动）：

- 向量总数接近千万级，或索引内存逼近单机容量；
- 查询 p95 延迟或召回率不满足产品 SLA 且调优无效；
- 检索服务需要独立于主库扩缩容，或向量负载已影响主库 OLTP 性能。

## 选项对比

| 维度 | pgvector | Qdrant | Milvus | Weaviate | Chroma |
|---|---|---|---|---|---|
| 定位 | PostgreSQL 扩展 | 专用向量库（Rust） | 分布式向量库 | 专用向量库（Go） | 轻量嵌入式库 |
| 规模舒适区 | 千万级以内 | 数亿级 | 十亿级 | 数亿级 | 百万级（原型） |
| 混合检索 | tsvector + SQL | 稀疏向量 + payload 过滤 | 稀疏 + 稠密 | BM25 + 向量内置 | BM25 |
| 元数据过滤 | SQL 全能力 | payload filter 强 | 标量过滤 | GraphQL 过滤 | 基础 |
| 运维成本 | 零新增组件 | 中（单服务，Docker/K8s） | 高（分布式集群） | 中 | 极低 |
| 迁移友好度 | — | 官方迁移工具支持 pgvector 源 | 无对等跨库工具 | 无对等跨库工具 | — |
| 适用 | 已用 PG、中小规模 | 性能敏感、过滤复杂 | 超大规模 | 知识库开箱即用 | 原型验证 |

## 理由

1. **初期规模在 pgvector 舒适区内**：数十万 chunk 远低于其上限，省掉一个独立组件的部署、监控、备份成本；向量与业务数据同库，"向量相似 + SQL 过滤"一条查询完成，且有事务一致性。
2. **退出路径有工具兜底**：Qdrant 官方维护迁移工具 [qdrant/migration](https://github.com/qdrant/migration)，pgvector 是一等支持源，一条 Docker 命令迁移且支持断点续传，迁移动作本身风险低。
3. **符合社区主流路径**："pgvector 起步 → 规模/性能不足再迁 Qdrant/Milvus"是 2025 年多个对比评测的共同推荐。
4. **可迁移性设计让决策可逆**：chunk registry + 抽象层 + 幂等灌库三件套，使"换向量库"从架构手术降级为运维操作，现在选 pgvector 不是锁定。

## 迁移方案（到达退出条件后执行）

### 迁移手段

- **迁 Qdrant**：优先用官方 `qdrant-migration` 工具的 `pg` 子命令直接搬运（表→Collection、行→Point、非向量列→payload，断点续传）：

  ```bash
  docker run --net=host --rm -it registry.cloud.qdrant.io/library/qdrant-migration pg \
      --pg.url 'postgres://user:pass@host:5432/dbname' \
      --pg.table 'chunks' \
      --pg.key-column 'id' \
      --qdrant.url 'http://target:6334' \
      --qdrant.collection 'chunks_v2'
  ```

- **迁 Milvus / Weaviate**：无对等跨库工具，从 chunk registry 执行标准灌库任务重新灌入（向量可导出复用，但建议顺带重新 embed 以消除历史版本混杂）。
- **无论哪条路径**，若迁移同时更换 embedding 模型，则必须全量重新 embed，工具搬运不适用（见"注意事项"）。

### 标准流程（Blue-Green 六步，零停机）

1. **基线记录**：记录旧库向量总数、10~50 条代表性查询的 top-k 结果，作为验收基准。
2. **建新库回填**：后台任务从 chunk registry 灌入新库，限速保护在线业务，checkpoint 可续传。
3. **双写**：新增/变更数据同时写新旧两库；双写队列按 `document_id` 分区保序，回填起点锚定一致快照（如 `pg_export_snapshot`），防止"快照后、双写前"的窗口丢数据。
4. **影子读验证**：用户仍读旧库，相同查询异步打新库，对比 Recall@k（门槛 ≥ 0.9）与过滤正确性。
5. **灰度切流**：feature flag 或 Qdrant collection alias（原子切换）按 5% → 50% → 100% 放量。
6. **回滚窗口**：旧库保留双写 ≥ 72 小时，指标异常一键切回；稳定后停止双写、下线旧库。

### 注意事项（踩坑清单）

- **换 embedding 模型 = 全量重灌**：模型 A 产出的向量对模型 B 的查询无意义（不是变差，是错误结果）；向量维度、instruction 前缀、chunking 策略变更同理。每条 chunk 的 `embedding_model_version` 与索引版本必须一致，查询服务启动时应校验。
- **距离度量语义差异**：pgvector 返回距离（越小越近），Qdrant 返回相似度（越大越近）；`vector_l2_ops` / `vector_ip_ops` 不会被迁移工具自动识别，须显式指定 `--qdrant.distance-metric`。
- **比召回，不比分数**：不同引擎的 ANN 实现与分数尺度不同，top-k 排名允许有差异，验收用 Recall@k / nDCG，不要求分数一致。
- **过滤语义差异**：pgvector 的 SQL WHERE 与目标库 payload filter 的表达能力不同（数组包含、范围、NULL 处理），迁移前逐条核对线上真实过滤条件。
- **元数据类型映射**：JSON 字段、数组、时间类型在目标库 payload 中的落型要抽样校验，防止类型强转丢失。
- **ID 一致性**：新旧库 point ID 必须由同一个 chunk 主键派生，保证双写覆盖与结果比对可对齐。

## 备选方案

**直接上 Qdrant**：若初期即确认需要高并发检索、独立扩缩容或复杂 payload 过滤，应新写 ADR 推翻本文，直接以 Qdrant 起步。

**托管向量服务（Pinecone / Zilliz Cloud 等）**：免运维但数据出域、按量计费，与自托管成本策略冲突时再评估。

**不做可迁移性设计、绑死 pgvector**：被否决。放弃 chunk registry 与抽象层会使未来迁移变成重写，节省的初期成本远小于迁移时的返工成本。

## 影响与后续动作

- `docs/03-设计/`：chunk 表数据模型须含原文 + 元数据 + `embedding_model_version`；VectorStore 接口契约在此定义。
- M2 骨架：`services/` 层落地 VectorStore 抽象与幂等灌库任务。
- embedding 模型选型：按 `docs/05-评估/embedding-选型实验方案.md` 执行，结论另写 ADR。
- 混合检索的具体实现（tsvector 配置、权重融合策略）随知识库功能在 M4 任务规格中定义。
